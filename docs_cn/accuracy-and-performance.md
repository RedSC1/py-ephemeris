# 精度与性能

`py-ephemeris` 是 Taiyin C++ 原生运行时的直接绑定。实际数值表现取决于选中的
路线、数据产品、时间尺度、观测者模型与计算选项，而不是由 Python 层单独决定。

当前仍是 preview 包。这里说明的是已知适用范围与待完成的验证项目，**不是**对所有
天体、历元和派生结果的统一精度承诺。

## 精度范围

| 路线或功能 | 当前说明 | 关键边界 |
| --- | --- | --- |
| 随包 DE442 衍生主要天体 OPM2 | 相对 DE442 源星历的典型 OPM2 重建差约为 **0.001 角秒** | 这只是状态压缩误差，不是最终视位置或站心位置误差。 |
| 外部 JPL BSP/SPK | 原生运行时直接计算用户提供的数据源 | 精度与范围遵从该源产品本身的模型和时间尺度限制。 |
| 内置半解析路线 | 约公历 -3000 至 +3000 年的无数据回退 | 它是回退路线，不应取代覆盖范围内的 OPM2 或 SPK。 |
| 随包小行星 OPM2 | 在各文件声明范围内提供直接精确路线 | 不应超出 manifest 覆盖区间外推。 |
| TKC1 开普勒 tier | 支持小天体的紧凑近似回退 | 精密天体测量、近接和掩星请使用 OPM2 或 SPK。 |
| 紧凑卫星回退 | 部分卫星系统无需外部内核即可计算 | 不是精密卫星星历；不同系统与区间的相对位置误差可从数十到数百公里。 |
| 恒星 | 从选中的 TSC1/TSF1 星表记录传播 | 依赖星表、历元、自行、视差、径向速度和观测者模型。 |

Python wheel 随附的 DE442 OPM2 覆盖约 1550–2650 年。范围外请通过诊断确认实际
路线；若精度重要，应添加合适的 SPK/OPM 数据。wheel 有意未附带大型卫星 SPK、EOP
表、完整恒星表和月缘地形数据。

### 派生结果的敏感性

事件时刻、方位高度、农历日期或食分接触时刻都属于派生结果，通常比单个笛卡尔状态
更敏感。结果还会受以下因素影响：

- UTC、UT1、TT、TDB 的转换，以及可用的 EOP / Delta-T 模型；
- 地球观测点、极移、大气与折射设置；
- 物理天体或质心路线及相应的中心修正；
- 日月食接触和可见性所用的月缘、地平线选项；
- 掠食、浅接触等几何条件，它们会放大微小的位置差异。

需要可复现的结果时，请记录包版本、C++ 内核修订、数据文件/产品 ID、路线与 flags、
观测者配置和输入时间尺度。若不希望 AUTO 因新加入数据而改变选择，请显式设置
`data_root`、`source_paths` 或 provider 优先级。

## 验证计划

C++ 内核已经对 OPM2 与其源星历进行重建验证。Python 首个稳定版本之前将补充对应的
Python 侧验证报告，至少包括：

1. 相对所选源产品的状态与视位置差；
2. 月相、升落及代表性日月食的事件时刻差；
3. 恒星位置和观测者坐标的回归用例；
4. 使用的数据文件、历元采样、指标和最差样本。

在此之前，`0.001 角秒` 只能理解为 OPM2 的典型重建量级，不能外推为全部输出的精度。

## 性能

性能需要同时测量 Python 调用开销与 C++ 原生计算成本。下面的基准使用安装后 wheel
内置的 DE442 衍生 OPM2 数据，**不是**内置半解析回退；凡标为 Python API 的项目都包含
wrapper 与结果对象创建。

### Linux 基线 — 2026-08-13

| 环境项 | 值 |
| --- | --- |
| 主机 | `grapefanta` |
| CPU | Intel Core i7-4785T，4 核 / 8 线程，标称 2.20 GHz（最高 3.2 GHz） |
| 系统 | Arch Linux，内核 7.0.10-arch1-1，x86_64 |
| 测试时 CPU 策略 | `schedutil`；采样频率 3.12 GHz |
| 内存 | 11 GiB |
| Python | CPython 3.14.5 |
| 编译器 / 构建 | GCC 16.1.1，scikit-build-core Release wheel |
| 数据 | 随包 DE442 衍生 OPM2、预生成 OPC、lite TSC1 星表 |

Python 项目均先预热，再以变化历元（`JD + n * 0.0125 d`）运行七轮取中位数，避免把
同一历元的缓存命中误当成代表性吞吐量。

| 工作负载 | 数据 / 选项 | 指标 | 结果 |
| --- | --- | --- | --- |
| 火星 `position.at_ut1` | 物理火星（`499`），默认视黄道坐标 | 7 × 8,000 次 | **50.59 µs/call**（19,768 calls/s） |
| 火星 `position.at_ut1` + speed | 物理火星，默认视黄道坐标 | 7 × 8,000 次 | **63.82 µs/call**（15,668 calls/s） |
| 火星 raw native binding | 物理火星、相同 flags，尚未创建 Python 结果对象 | 7 × 8,000 次 | **39.10 µs/call** |
| 火星 `state_at_ut1` | 物理火星，位置、速度与加速度 | 7 × 8,000 次 | **71.26 µs/call**（14,034 calls/s） |
| 火星系形心 `position.at_ut1` | DE442 直接形心（`4`） | 5,000 次 | **约 34.5 µs/call** |
| OPM2 裸 ICRF state | 火星系形心，native C++ probe | 20,000 次 | **1.45 µs/call** |
| OPM2 视位置 | 火星系形心，native C++ probe | 20,000 次 | **17.52 µs/call** |
| OPM2 视位置 | 物理火星，native C++ probe | 20,000 次 | **32.23 µs/call** |

作为同机量级参考，使用相同解释器与变化历元循环时，`pyswisseph 2.10.3.2` /
Swiss Ephemeris 20230604 的 `calc_ut(Mars, FLG_SWIEPH | FLG_SPEED)` 为
**13.03 µs/call**，赤道 XYZ 变体为 **13.13 µs/call**。这不是精度等价声明：两边的数据
产品与视位置约定仍各自独立。

这组拆分是有意的：OPM2 直接求值很快；公开的物理火星结果还会加上紧凑的
Phobos/Deimos 质心修正和标准视位置管线，Python 随后还会创建诊断与结果对象。这些数字
只是低功耗 Haswell 时代机器的回归基线，不是对现代桌面或服务器吞吐量的通用承诺。

### 基准规则

后续正式结果会说明 CPU、操作系统、Python 版本、编译器/构建类型、包与内核修订、数据
产品、预热规则、循环次数，以及是否包含 Python 对象创建。单次与 batch 会分开报告，
避免把缓存的 native loop 和 Python 逐次循环混为同一指标。

在此之前，请对自己真正关心的工作负载做 profile。复用 `Ephemeris` 与 calculation
context，为外部数据目录保留 OPC，并在多历元共享同一配置时优先使用 batch API。
