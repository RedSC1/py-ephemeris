# 精度与性能

本文测试的是安装后的 **Python 绑定**，不是 C++ 裸调用。除非某段明确讨论 OPM2
数据生成指标，下面的验证和性能测量都通过 Taiyin 的公开 Python API 完成，耗时包含
Python 到 pybind 的调用以及公开结果对象的构造。表格不混入裸 C++ 基准，也不进行
跨库速度对比。

`py-ephemeris` 是 Taiyin C++ 原生运行时的直接绑定。实际数值表现取决于选中的
路线、数据产品、时间尺度、观测者模型与计算选项，而不是由 Python 层单独决定。

当前仍是 preview 包。这里说明的是已知适用范围与待完成的验证项目，**不是**对所有
天体、历元和派生结果的统一精度承诺。

## 精度范围

| 路线或功能 | 当前说明 | 关键边界 |
| --- | --- | --- |
| 随包 DE442 衍生主要天体 OPM2 | 相对 DE442 源星历的典型 OPM2 重建差约为 **0.001 角秒** | 这只是状态压缩误差，不是最终视位置或站心位置误差。 |
| 外部 JPL BSP/SPK | 原生运行时直接计算用户提供的数据源 | 精度与范围遵从该源产品本身的模型和时间尺度限制。 |
| 内置半解析路线 | 约公历 -3000 至 +3000 年的无数据回退 | 它是回退路线，不应取代覆盖范围内的 OPM2 或 SPK。 |
| 随包小行星 OPM2 | 在各文件声明范围内提供直接精确路线 | 不应超出 manifest 覆盖区间外推。 |
| TKC1 开普勒 tier | 支持小天体的紧凑近似回退 | 精密天体测量、近接和掩星请使用 OPM2 或 SPK。 |
| 紧凑卫星回退 | 部分卫星系统无需外部内核即可计算 | 不是精密卫星星历；不同系统与区间的相对位置误差可从数十到数百公里。 |
| 恒星 | 从选中的 TSC1/TSF1 星表记录传播 | 依赖星表、历元、自行、视差、径向速度和观测者模型。 |

Python wheel 随附的 DE442 OPM2 覆盖约 1550–2650 年。范围外请通过诊断确认实际
路线；若精度重要，应添加合适的 SPK/OPM 数据。wheel 有意未附带大型卫星 SPK、EOP
表、完整恒星表和月缘地形数据。

### 派生结果的敏感性

事件时刻、方位高度、农历日期或食分接触时刻都属于派生结果，通常比单个笛卡尔状态
更敏感。结果还会受以下因素影响：

- UTC、UT1、TT、TDB 的转换，以及可用的 EOP / Delta-T 模型；
- 地球观测点、极移、大气与折射设置；
- 物理天体或质心路线及相应的中心修正；
- 日月食接触和可见性所用的月缘、地平线选项；
- 掠食、浅接触等几何条件，它们会放大微小的位置差异。

需要可复现的结果时，请记录包版本、C++ 内核修订、数据文件/产品 ID、路线与 flags、
观测者配置和输入时间尺度。若不希望 AUTO 因新加入数据而改变选择，请显式设置
`data_root`、`source_paths` 或 provider 优先级。

## Python 绑定验证状态

截至 2026-08-13，主 wheel 回归套件完成 **79/79 项测试**，其中日月食子集为
**8/8 项**。单独构建的八字 wheel 完成 **4/4 项测试**，包括分别参数化的男女起运
用例。大部分测试通过公开 facade；少量 binding/callback 测试会有意直接访问 `_native`，
用于验证扩展边界本身。测试覆盖时间转换、位置与状态、观测者配置、恒星、事件与
可见性、日月食与掩星、轨道结果、占星、中国历法 facade 和八字扩展集成。
固定数值集成用例通常显式选择 C++ 源码树中的 DE441 600 年 fixture，避免随包优先级
变化时悄悄换路线；随包数据测试及下方精度脚本则明确使用 wheel 内置的 DE442 产品。

这些是行为回归测试，不代表 79 项彼此独立的绝对天体测量精度声明。目前的验证层次为：

1. OPM2 生成阶段将重建状态与源星历比较；
2. 安装后的 Python 包通过公开 API 实际调用这些路线；
3. 固定的事件、日月食、历法、恒星和观测者用例检测绑定与内核行为变化；
4. 可复现报告明确记录数据产品和实际路线。

`0.001 角秒` 是 OPM2 相对源星历的典型重建指标。Python wheel 因随附该产品而在此
列出它，但它不是 Python wrapper 误差，也不能当作全部视位置、站心位置和派生结果的
统一上限。

## 性能

下面只测安装后 wheel 的公开 Python 方法，使用随包 DE442 衍生 OPM2，并通过默认
AUTO 路线补齐必要的形心修正。每个数字都包含 pybind 调度和 Python 可见结果对象构造。

### Linux Python 基线 — 2026-08-13

| 环境项 | 值 |
| --- | --- |
| 主机 | `VM-0-14-ubuntu`（KVM 虚拟机） |
| CPU | 4 vCPU，Intel Xeon Platinum 8255C，2.50 GHz |
| 系统 | Ubuntu，Linux 6.8.0-101-generic，x86_64 |
| 内存 | 3.6 GiB |
| Python | CPython 3.12.3 |
| 编译器 / 构建 | GCC 13.3.0，scikit-build-core Release wheel |
| 数据 | 随包 DE442 衍生 OPM2、预生成 OPC、lite TSC1 星表 |
| 修订 | Python `b8fee41`；Taiyin C++ `06ea3f06` |

位置类负载每轮使用 8,000 个预先创建的变化历元（`JD + n * 0.0125 d`）。日食地图和
局部情况使用固定食甚历元；搜索接口重复相同起点，但每次都执行完整搜索。全部项目先
预热，计时循环中暂时关闭循环垃圾回收，运行七轮取中位数。

| 工作负载 | 数据 / 选项 | 指标 | 结果 |
| --- | --- | --- | --- |
| 火星 `position.at_ut1` | 物理火星（`499`），默认视黄道坐标 | 7 × 8,000 次 | **45.22 µs/call** |
| 火星 `position.at_ut1` + speed | 物理火星，默认视黄道坐标 | 7 × 8,000 次 | **60.39 µs/call** |
| 火星 `state_at_ut1` | 物理火星，位置、速度与加速度 | 7 × 8,000 次 | **82.62 µs/call** |
| 火星系形心 `position.at_ut1` | 直接形心（`4`） | 7 × 8,000 次 | **27.79 µs/call** |
| 八个物理行星逐个调用 | 每个天体成本 | 7 × 8,000 个历元 | **133.87 µs/body** |
| 八个物理行星 `batch_at_ut1` | 每个天体成本 | 7 × 8,000 个历元 | **132.13 µs/body** |
| `solar_eclipse_where_at_ut1` | 2024-04-08 日食的固定全球几何 | 7 × 3,000 次 | **39.75 µs/call** |
| `local_solar_circumstances_at_ut1` | Dallas 观测点、固定事件历元 | 7 × 2,000 次 | **30.81 µs/call** |
| `next_solar_at_ut1` | 下一次全球日食搜索 | 7 × 80 次 | **1,002.67 µs/call** |
| `next_local_solar_at_ut1` | Dallas 的下一次地方日食搜索 | 7 × 50 次 | **1,850.34 µs/call** |

这些数字只是该虚拟机的回归基线，不是可移植的吞吐量承诺。物理火星项目包含形心修正
路线与正常视位置管线；火星系形心项目不需要物理天体重建。八行星负载的主要成本在
原生计算，因此 `batch_at_ut1` 在这里每个天体只节省约 1.3%；batch 仍适合一次紧凑地
取得多个结果，但本文不把它宣传成数量级加速。

下面的多线程部分测量的是另一项指标：多个 worker 共享一个已经配置完成的
`EphemerisContext` 时的吞吐量。它预先创建一组固定历元，在 1、2、4、6、8 个线程下
执行相同总量的公开 `position.at_ut1` 调用，并消费每次调用返回的坐标和 `ResultFlag`。
计时开始前完成配置，所有 worker 结束后再关闭 context。每个线程数报告每次调用的中位数
耗时，并使用：

```text
speedup = 单线程耗时 / 当前线程数耗时
```

原生计算会释放 GIL，但加速比取决于 CPU 容量、数据缓存、Python 版本、工作负载和系统
当时的其他活动。并不保证一定加速；低于 1 的结果同样能反映该机器上的并发开销。脚本会
打印线程数和固定工作量，便于比较：

```bash
python benchmarks/python_api.py --threaded-iterations 8000 --threaded-rounds 7
```

一次使用随包 OPM2 数据的本地代表性测试表明，标量 `position.at_ut1` **不能**从
Python 多线程获得加速。固定执行 8,000 次调用，相对于单线程的中位吞吐比为：

| context 组织方式 | 2 线程 | 4 线程 | 8 线程 |
|---|---:|---:|---:|
| 所有线程共享一个 context | 0.73x | 0.54x | 0.47x |
| 每线程使用独立 clone context | 0.75x | 0.55x | 0.48x |

两行几乎相同，说明瓶颈不是 context 的诊断快照。OPM2 状态求值本身非常快，Python
线程调度以及进程级星历 catalog/segment cache 的竞争反而超过了并行收益。这类工作应
优先顺序调用标量接口，或使用 batch 接口。

如果每项原生计算足够重，多线程仍然有效。作为诊断实验，半解析 provider 的“搜索下次
日食”在 2、4、8 个线程下分别达到约 1.79x、2.69x、3.60x；同一搜索改用随包 OPM2
路线后，则因反复访问共享 OPM2 cache 而随线程增多变慢。这说明 GIL 确实已经释放，
但这些数字不是跨机器的性能承诺。

本节的所有 worker 都使用同一个已经配置好的 context。计时期间不要修改配置、注册回调、
修改日历或 chart，也不要关闭 context。

### 基准规则

可复现脚本为 [`benchmarks/python_api.py`](../benchmarks/python_api.py)：

```bash
python benchmarks/python_api.py --batch-iterations 8000
python benchmarks/python_accuracy.py
python benchmarks/python_accuracy.py --de442-bsp /path/to/de442.bsp
```

它只 import `taiyin` 并调用公开 API。后续结果应继续记录环境、数据产品、AUTO/provider
策略、预热、循环次数和结果对象口径；单次与 batch 必须分开报告。

在此之前，请对自己真正关心的工作负载做 profile。复用 `Ephemeris` 与 calculation
context，为外部数据目录保留 OPC，并在多历元共享同一配置时优先使用 batch API。
